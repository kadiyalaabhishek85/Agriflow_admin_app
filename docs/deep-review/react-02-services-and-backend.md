# Deep review — React website services, backend integration and project configuration (leaf 1.3.2)

## Scope

This leaf covers everything under `agriflow/agriflow-web` **outside** `src/`: the service layer (readable for analysis, but the UI documentation belongs to leaf-1.3.1), the Supabase edge functions, the SQL migrations, the root-level scripts, the deployment/build configuration and the markdown documentation, plus the project configuration files. The review document itself is the only file written.

Ground truth is `openapi_dump.json` in the workspace root (94 paths). Where the code reaches for a capability the live FastAPI contract does not expose, the capability is marked with the exact literal sentence `Backend API required - to be supplied by Syed.` Where the React site talks to Supabase instead of the FastAPI backend, that divergence is reported as a finding rather than smoothed over.

The single most important structural fact found in this scope: **no file anywhere in `agriflow/agriflow-web` — including `src/` — contains the string `/api/v1`, `FastAPI`, or the live backend host.** A recursive search for `api/v1|agriflow-backend` across every file in the project returns zero matches. The React site is a Supabase-only application (PostgREST + RPC + Storage + Edge Functions + Supabase Auth) and has no HTTP client (no `axios`, no `fetch` wrapper to a REST base URL) in `package.json`. Every FastAPI endpoint named below therefore exists in the authoritative dump but is *consumed by nobody* in this project.

## Service layer

**Base URL and client.** There is exactly one backend client in the application: `createClient(VITE_SUPABASE_URL, VITE_SUPABASE_ANON_KEY)` (`src/lib/supabase.js:3-6`). Both values fall back to the empty string, and `createClient('','')` throws at startup, so an unset `.env` fails loudly at runtime; no `.env.example` documents either key (`.gitignore:30-31` ignores `.env` and `.env.local`, and nothing replaces them). There is no FastAPI base URL, no `Authorization` header builder for a REST API, and no token refresh logic for anything except Supabase Auth.

**Two data-access styles.** Five services route everything through a Supabase Edge Function action bus (`{ action, payload }`); the other six call PostgREST tables, `supabase.rpc(...)` or Storage directly with the anon key plus whatever JWT Supabase attaches.

- `adminService` (`src/services/adminService.js:3-16`) builds `{ action, payload: { ...payload, callerRole } }` for `admin-api`. The role is read out of `sessionStorage.getItem('agro_user')` (`adminService.js:7-8`) — i.e. the *client* declares its own privilege. Error mapping is `if (error) throw error; if (data?.error) throw new Error(data.error)` (`adminService.js:13-14`), which discards HTTP status codes entirely: a 403, a 404 "Action not found" and a 500 all surface to the UI as the same `Error`. Actions: `getDashboard`, `getFarmers`, `getFarmerDetails`, `deleteFarmer`, `getManagers`, `updateManagerStatus`, `updateManager`, `getAuditLogs`, `getReportsMonthly`, `getSeeds`, `getWarehouses`, `createSeed`, `updateSeed`, `deleteSeed`, `getSeedPurchases`, `updateSeedPurchaseStatus` (`adminService.js:19-123`). Three methods instead call `admin-create-user` with an explicit `Authorization: Bearer ${session?.access_token}` (`adminService.js:34-36`, `62-64`, `82-84`) — an inconsistency that only exists because the comment at `adminService.js:5-6` asserts `functions.invoke()` sends the anon key rather than the user JWT.
- `authService` (`src/services/authService.js:5-77`): phone identifiers are first resolved to an email via the `auth-api` `resolvePhoneToEmail` action (`authService.js:11-19`), then `supabase.auth.signInWithPassword` (`authService.js:21-24`), then the profile is loaded via `auth-api` `getUserData` (`authService.js:30-32`). Business rules enforced client-side: farmers may not log in with an email (`authService.js:45-48`), and any status other than `active` forces a sign-out (`authService.js:51-55`). The token and a derived user object are mirrored into `sessionStorage` under `agro_token` / `agro_user` (`authService.js:59-69`). Registration is `supabase.auth.signUp` (`authService.js:83-89`) followed by the `auth-api` `registerDatabaseUser` action (`authService.js:93-100`). `changePassword(phone, oldPassword, newPassword)` accepts the current password but never sends or verifies it — it calls `supabase.auth.updateUser({ password })` and then clears `first_login` (`authService.js:143-156`); the authoritative contract for this operation is `API: POST /api/v1/auth/change-password`. `verifyOtp` is a stub that always throws (`authService.js:183-186`) even though `API: POST /api/v1/auth/send-otp` and `API: POST /api/v1/auth/verify-otp` exist. `resetPassword` uses `supabase.auth.resetPasswordForEmail` (`authService.js:109-115`) rather than `API: POST /api/v1/auth/forgot-password/send-otp` and `API: POST /api/v1/auth/forgot-password/reset`.
- `farmerService` (`src/services/farmerService.js:3-10`) invokes `farmer-api` for 20 actions (`farmerService.js:13-115`) but breaks the pattern twice: `getWarehouseSlots` reads the `warehouse_slots` table directly (`farmerService.js:62-71`) and `bookDeliverySlot` calls `supabase.rpc('create_booking_slot', ...)` directly (`farmerService.js:75-83`), duplicating logic that `farmer-api` also exposes (`supabase/functions/farmer-api/index.ts:162-185`).
- `managerService` (`src/services/managerService.js:3-10`) is a pure action bus over `manager-api` with 17 actions (`managerService.js:13-79`) — approve/reject farmers, bank requests, visit scheduling, booking status, inspection, procurement, grain-sale review and payment.
- `cropService` (`src/services/cropService.js:4-33`), `ledgerService` (`src/services/ledgerService.js:4-87`), `marketService` (`src/services/marketService.js:4-64`), `notificationService` (`src/services/notificationService.js:4-35`), `warehouseService` (`src/services/warehouseService.js:4-104`) and `publicService` (`src/services/publicService.js:4-18`) bypass edge functions entirely and hit PostgREST/RPC directly with the anon key, relying 100% on RLS. `storageService` (`src/services/storageService.js:19-94`) writes to Supabase Storage buckets and returns public URLs (`storageService.js:59-61`) rather than signed ones for the default path.

Four capabilities the service layer implements have **no** counterpart in the 94-path dump:

- Deleting a farmer account and its dependent rows (`adminService.deleteFarmer` → `admin-api` `deleteFarmer`). Backend API required - to be supplied by Syed.
- Editing a manager's name/email/phone (`adminService.updateManager` → `admin-api` `updateManager`); the contract only carries status and password-reset. Backend API required - to be supplied by Syed.
- Editing or deleting an individual market rate (`marketService.updateRate`, `marketService.deleteRate`); the contract only has list and create. Backend API required - to be supplied by Syed.
- Creating and editing manual ledger transactions (`ledgerService.createTransaction`, `ledgerService.updateTransaction`); the contract only lists and pays transactions. Backend API required - to be supplied by Syed.

## Supabase edge functions

Five functions live under `supabase/functions/`, all written the same way: Deno `serve`, a permissive `Access-Control-Allow-Origin: *` CORS block, a JSON `{ action, payload }` body, an if-ladder over actions, `404 { error: 'Action not found' }` for unknown actions and a catch-all `500 { error }` (`admin-api/index.ts:389-393`, `farmer-api/index.ts:243-247`, `manager-api/index.ts:277-280`, `auth-api/index.ts:456-461`). None of them has a versioned `supabase/config.toml`, so `verify_jwt` and per-function secrets are configured only in the hosted project, not in the repository.

1. **`auth-api`** (`supabase/functions/auth-api/index.ts`) — HTTP contract: `POST` with `{ action, payload }`, actions `getUserData`, `registerDatabaseUser`, `setFirstLoginFalse`, `updateProfile`, `resolvePhoneToEmail` (`index.ts:43`, `206`, `382`, `408`, `432`). Secrets read: `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` (`index.ts:23-25`). It builds two clients — an RLS-scoped client forwarding the caller's `Authorization` header (`index.ts:30-32`) and a service-role client that bypasses RLS (`index.ts:35`) — and then performs **every** read/write through the service-role client, so no action is actually protected by the caller's JWT. Invoked by `authService` for login, registration, profile edits and first-login clearing.
2. **`admin-api`** (`supabase/functions/admin-api/index.ts`) — actions `getDashboard`, `getFarmers`, `getFarmerDetails`, `deleteFarmer`, `getManagers`, `updateManagerStatus`, `updateManager`, `getAuditLogs`, `getReportsMonthly`, `getSeeds`, `getWarehouses`, `createSeed`, `updateSeed`, `deleteSeed`, `getSeedPurchases`, `updateSeedPurchaseStatus`. Secrets: `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` (`index.ts:15-16`, `25`). Reads go through the RLS-scoped client; the destructive `deleteFarmer` path and seed writes go through `adminDb` (service role, `index.ts:25`). Authorization is `getCallerRole()`, which simply returns `payload?.callerRole` (`index.ts:236-238`) — the comment at `index.ts:229-235` explains that this is deliberate because the invoke helper cannot supply a verifiable user JWT. `deleteFarmer` cascades deletes across `notifications`, `audit_logs`, `transactions`, `bank_change_requests`, `crop_inspections`, `booking_slots`, `grain_sales`, `seed_purchases`, `farm_visits`, `crops`, `farmer_profiles`, `users`, `profiles` and finally `auth.admin.deleteUser` (`index.ts:114-142`) with no transaction and no role check at all.
3. **`admin-create-user`** (`supabase/functions/admin-create-user/index.ts`) — the only function that authenticates properly: it requires an `Authorization` header (`index.ts:16-19`), validates it with `clientSupabase.auth.getUser()` (`index.ts:31-34`), then loads the requester from `profiles` and requires `['manager','super_admin']` (`index.ts:37-45`). Actions: user creation for roles `farmer`/`manager` only (`index.ts:89-91`) and `resetPassword`, restricted to `super_admin` (`index.ts:50-53`). Secrets: `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, `SUPABASE_ANON_KEY` (`index.ts:21-26`). It writes a bcrypt hash into the legacy `users.password_hash` column (`index.ts:143`, `162-167`) and returns `200` with `{ error }` bodies for ordinary validation failures (`index.ts:80`, `84`, `90`, `106`, `117`) instead of 4xx.
4. **`farmer-api`** (`supabase/functions/farmer-api/index.ts`) — 20 actions covering profile, bank change, dashboard, crops, seeds, grain sales, warehouses, slots, bookings, transactions, visits, notifications and market rates (`index.ts:25-241`). Secrets: `SUPABASE_URL`, `SUPABASE_ANON_KEY` only (`index.ts:15-16`) — it never uses the service role, so all data access is RLS-gated by the forwarded header. Its `requestBankChange` tries to notify admins with `supabase.from('users').select('id').in('role', ['admin','manager','super_admin'])` (`index.ts:57`) through that same RLS-scoped client, which for a farmer returns only their own (non-matching) row — so the loop at `index.ts:58-71` never runs for a real farmer.
5. **`manager-api`** (`supabase/functions/manager-api/index.ts`) — 17 actions (`index.ts:25-275`) that mostly delegate to `SECURITY DEFINER` RPCs: `approve_farmer` (`index.ts:45`), `review_bank_request` (`index.ts:71`), `update_booking_yield` (`index.ts:173`), `update_booking_status` (`index.ts:181`), `procure_grain_booking` (`index.ts:199`), `inspect_crop` (`index.ts:217`), `procure_crop` (`index.ts:246`), `review_grain_sale` (`index.ts:253`), `pay_grain_sale` (`index.ts:267`). Secrets: `SUPABASE_URL`, `SUPABASE_ANON_KEY` (`index.ts:15-16`). There is no role check anywhere in this function: any authenticated caller who can reach it can attempt manager operations, with the database as the only gate.

**Invocation.** From the browser, every function is reached with `supabase.functions.invoke('<name>', { body })` (for example `adminService.js:10`, `authService.js:11`, `farmerService.js:4`, `managerService.js:4`, `adminService.js:29`). Because the URL is derived from `VITE_SUPABASE_URL`, the functions are callable by anyone holding the project's anon key.

## Database and migrations

Eleven migrations are shipped under `supabase/migrations/`, and `supabase/migrations_backup/` holds **eleven byte-identical copies** (MD5-verified for every file) — a duplicated tree with no documented purpose that will double-apply if a tool globs `supabase/**/*.sql`.

- `20260710052900_harden_rls_policies.sql` — closes anonymous write access to `warehouses`, `warehouse_slots`, `warehouse_inventory`, `seed_warehouses` by splitting an old `ALL USING (true)` policy into public `SELECT` + `manager`/`super_admin` writes (`:9-31`); enables RLS on `admin_profiles` (`:35`), `distributor_orders` (`:39-42`) and `otps` (`:46`, deny-all).

Note the update/delete policies are not owner-scoped (`:19-25`), so any authenticated user can overwrite or delete any object in those buckets.
- `20260710060000_fix_rls_recursion.sql` — the load-bearing policy file. Defines `current_app_user_id()`, `current_user_role()`, `current_profile_role()` as `SECURITY DEFINER` helpers (`:17-45`) and rewrites **every** table policy in terms of them: `users` (`:55-58`), `profiles` (`:61-74`), `admin_profiles` (`:77-80`), `audit_logs` (`:83-86`), `bank_change_requests` (`:89-92`), `booking_slots` (`:95-98`), `crop_inspections` (`:101-104`), `crops` (`:107-110`), `distributor_orders` (`:113-116`), `farm_visits` (`:119-123`), `farmer_profiles` (`:126-129`), `grain_sales` (`:132-135`), `market_rates` (`:138-141`), `notifications` (`:144-147`), `seed_purchases` (`:150-153`), `seed_warehouses` (`:156-159`), `seeds` (`:162-165`), `transactions` (`:168-171`), `warehouse_inventory` (`:174-177`), `warehouse_slots` (`:180-183`), `warehouses` (`:186-189`). ## Findings

### Shipped code

1. **P0 — Self-service privilege escalation through RLS.** `users_policy` is `FOR ALL USING (uuid = auth.uid() OR current_user_role() IN ('manager','super_admin'))` (`supabase/migrations/20260710060000_fix_rls_recursion.sql:55-58`) and the profiles update policy is `auth.uid() = id OR ...` (`:66-69`). RLS restricts *rows*, not *columns*, and the repository contains no column-level `REVOKE` for either table (`data_dump.sql` is empty; the only grants in the tree are for three helper functions at `:47-52`). A farmer who can call PostgREST can therefore update their own `users.role` — or their own `profiles.role` — to `super_admin`. `current_user_role()` (`:27-35`) and `current_profile_role()` (`:37-45`) read those exact columns, so the escalation would unlock every policy in the file.
2. **P0 — `handle_new_user()` trusts client-supplied signup metadata for role and status.** `COALESCE(NEW.raw_user_meta_data->>'role','farmer')` and a non-farmer default of `'active'` (`supabase/migrations/20260711170000_fix_signup_trigger_bugs.sql:60-61`, `:85-86`) mean a self-registration that sets `user_metadata.role = 'super_admin'` creates an active super-admin row in both `users` and `profiles`. `supabase.auth.signUp` forwards arbitrary client metadata, and `src/services/authService.js:83-89` is only one payload change away from it.
3. **P0 — `admin-api` authorises on a client-controlled field.** `getCallerRole()` returns `payload?.callerRole` (`supabase/functions/admin-api/index.ts:236-238`), sourced from `sessionStorage` (`src/services/adminService.js:7-8`). Seed creation/deletion/price changes (`index.ts:262-265`, `298-301`, `318-320`), manager status edits, monthly reports, audit logs and the unguarded `deleteFarmer` cascade (`index.ts:82-151`) are all reachable by anyone with the anon key and a forged JSON body, and the destructive paths run under the service-role key (`index.ts:25`).
4. **P0 — `auth-api` never uses the caller's identity.** Every action executes through `supabaseAdmin` (`supabase/functions/auth-api/index.ts:35`, used at `:53`, `:128`, `:254`, `:386`, `:413`, `:441`). `updateProfile` and `setFirstLoginFalse` therefore accept any `authUserId`/`userId` from an unauthenticated body, and `resolvePhoneToEmail` (`:432-454`) is an unauthenticated phone→email oracle that also synthesises `${phone}@agriseq.local` addresses (`:452`).
5. **P1 — Booking approval is broken by migration drift.** The UI sends `'confirmed'` (`src/components/shared/NotificationCenter.jsx:75`, `src/pages/admin/BookingSlots.jsx:48`), but the current `update_booking_status` only accepts `approved`, `rejected`, `cancelled` and returns `{ error: 'Invalid status payload: ...' }` otherwise (`supabase/migrations/20260720151000_remove_razorpay_and_procurement_update.sql:155`, `:176`, `:205`, `:233-235`), which `manager-api` rethrows (`supabase/functions/manager-api/index.ts:189`).
6. **P1 — `inspect_crop` is unreachable.** It refuses any slot whose status is not `'delivered'` (`supabase/migrations/20260714080000_seed_purchase_notify_and_units.sql:112-114`), but no shipped code path can set `'delivered'` any more: the replacement `update_booking_status` only writes `approved`/`rejected`/`cancelled` (`20260720151000:155-158`, `:177-179`, `:206-208`) and `procure_grain_booking` writes `completed`/`cancelled` (`20260720151000:298`).
7. **P1 — Role vocabulary mismatch: `admin` exists in code, never in RLS.** `admin-api` accepts `'admin'` (`supabase/functions/admin-api/index.ts:263`, `:298`, `:318`) and `farmer-api` notifies `'admin'` users (`supabase/functions/farmer-api/index.ts:57`), yet every RLS array is `ARRAY['manager','super_admin']` (`supabase/migrations/20260710060000_fix_rls_recursion.sql:57`, `:63`, `:85`, `:164`, `:188`). Because `admin-api` reads through the RLS-scoped client (`admin-api/index.ts:19-21`), an `admin`-role user gets empty results from `getFarmers`, `getAuditLogs` and `updateSeedPurchaseStatus` while the edge function's own gate lets them through.
8. **P1 — `SECURITY DEFINER` RPCs with no caller check.** `purchase_seeds` (`20260720152500:5-88`), `inspect_crop`, `update_booking_yield`, `procure_crop`, `update_booking_status`, `procure_grain_booking`, `create_booking_slot`, `process_payment` (called at `src/services/ledgerService.js:81`) and friends never verify `auth.uid()` or role, and no migration in this repository revokes `EXECUTE` from `anon`. Any default `PUBLIC` execute grant makes them callable by anonymous clients with arbitrary `p_farmer_id`/`p_admin_id` arguments.
9. **P1 — Signature verification is stored, not verified.** `verify_and_complete_payment` accepts `p_signature` and simply inserts it (`supabase/migrations/20260720140000_razorpay_payment_tables.sql:130-136`, `:202-204`) with no HMAC comparison against a gateway secret; the "never trust frontend" comment at `:96` applies to price only. (The tables were subsequently dropped by `20260720151000:3-7`, so this is now dead code — but it documents the payment-verification posture and may be reinstated.)
10. **P2 — Farmer-side admin notifications silently never fire.** `farmer-api` reads `users` for admin ids through the farmer's own RLS view (`supabase/functions/farmer-api/index.ts:57-71`), so the result is empty and no notification row is created; only the `SECURITY DEFINER` trigger (`supabase/migrations/20260714090000:39-55`) notifies `super_admin`. Managers never learn of a bank change request from this path.
11. **P2 — `purchase_seeds` return shape and messaging drift.** `20260714080000:81-86` returned `id`, `invoice_number`, `total_amount`, `message`; `20260720152500:86` returns only `success` and `id`, while the farmer notification text hard-codes "Pay at Warehouse" regardless of the chosen payment method (`20260720152500:77-78`), and `upi_id`/`transaction_id` are no longer persisted on `seed_purchases` (`20260720151000:10-11` vs `20260714080000:51-54`).
12. **P2 — Error handling collapses status codes.** All four action-bus services map HTTP 4xx/5xx, `{ error }` bodies and unknown-action 404s into one generic `Error` (`src/services/adminService.js:13-14`, `src/services/farmerService.js:7-8`, `src/services/managerService.js:7-8`, `src/services/authService.js:34-37`), so the UI cannot distinguish "not allowed" from "not found" from "server down". `admin-create-user` compounds this by returning `200` with an `error` body for validation failures (`supabase/functions/admin-create-user/index.ts:80`, `84`, `90`, `106`, `117`).
13. **P2 — Authentication divergence and a no-op password check.** The web app ignores the OTP and phone-login flow the backend provides (`API: POST /api/v1/auth/send-otp`, `API: POST /api/v1/auth/verify-otp`, `API: POST /api/v1/farmer/auth/login`) and instead resolves phone→email (`src/services/authService.js:11-19`) to reuse `supabase.auth.signInWithPassword`; `verifyOtp` throws unconditionally (`src/services/authService.js:183-186`); `changePassword` takes `oldPassword` and never validates it (`src/services/authService.js:143-147`).
14. **P2 — Default credentials shipped in the client bundle.** `manager_default_creds` (`phone=8888888888, password=Manager@123`) and `super_admin_default_creds` (`phone=9999999999, password=Super@123`) are present in all four locales (`public/locales/en/translation.json:274`, `:290`; `public/locales/hi/translation.json:250`, `:266`; `public/locales/ta/translation.json:268`, `:284`; `public/locales/te/translation.json:250`, `:266`), directly contradicting the "No hardcoded credentials" claim at `SECURITY_IMPLEMENTATION.md:345`.
15. **P3 — Duplicate migration tree.** `supabase/migrations_backup/` is a 11-file, MD5-identical copy of `supabase/migrations/`; any tool that globs `supabase/**/*.sql` will apply everything twice.
16. **P3 — Dead or inconsistent shipped config.** `netlify/functions/api.js:7-8` requires a missing package and a missing `server/`; `vercel.json:4-6` points at a non-existent `api/index.cjs`; `config/mongodb.js:1` requires an uninstalled `mongoose`; `package.json:2` still names the project `agro-platform` and exposes no `server` script; `index.html:7` titles the site "Sri Siva Sai Seeds" while `README.md:1` calls it "AgroSeq - AgriFlow ERP".
17. **P3 — Documentation describes a backend that does not exist here.** `Backend_Technical_Specification.md:1080-1089`, `SECURITY_IMPLEMENTATION.md:204-258`, `RATE_LIMITING.md` and `VALIDATION.md:608` all document an Express/Node server (`server/index.js`, Helmet, `JWT_SECRET`, `localhost:5000`) whose endpoints (`GET /api/admin/farmers` etc., `Backend_Technical_Specification.md:389`) match neither the FastAPI contract nor the Supabase actions in use. `README.md:41` omits FastAPI entirely.

## Recommendations

**P0 — close the privilege-escalation paths.**
1. Revoke `UPDATE` on `public.users` and `public.profiles` from `authenticated` (or add column-level `REVOKE`s for `role`, `status`, `first_login`, `app_user_id`) and confirm on the live database that no such grant exists today; then re-verify `current_user_role()` / `current_profile_role()`.
2. Stop trusting `raw_user_meta_data` for `role`/`status` in `handle_new_user()`; hard-code `farmer`/`pending` for self-signup and let only the service role (via `admin-create-user`) assign privileged roles.
3. Re-derive caller role server-side in `admin-api` from a verified JWT — the pattern already exists and works in `admin-create-user/index.ts:31-45` — and delete `getCallerRole()`/`callerRole`.
4. Make `auth-api` scope every action to `auth.getUser()` of the forwarded header instead of `supabaseAdmin`; gate `updateProfile`/`setFirstLoginFalse` on the caller's own id and drop or authenticate `resolvePhoneToEmail`.
5. Revoke `EXECUTE` on all `SECURITY DEFINER` RPCs from `anon` (and from `authenticated` where the caller must be a manager) and re-grant explicitly.

**P1 — repair the broken business flows.**
6. Reconcile `update_booking_status` with the UI: either accept `confirmed` again or change the callers, and remove the dead `'delivered'` requirement from `inspect_crop`.
7. Unify the role vocabulary: decide whether `admin` is a role, then make the edge-function gates, `farmer-api` notification queries and every RLS `ARRAY[...]` agree.
8. Fill the four backend gaps: farmer deletion (Backend API required - to be supplied by Syed.), full manager editing (Backend API required - to be supplied by Syed.), market-rate edit/delete (Backend API required - to be supplied by Syed.), manual transaction create/edit (Backend API required - to be supplied by Syed.). Until then, mark those UI actions unavailable rather than failing at runtime.
9. Decide the FastAPI-vs-Supabase strategy explicitly: either point the React site at `API: GET /api/v1/...` endpoints, or record in `AGENTS.md` that this project is Supabase-native and keep the two backends' data models in sync by contract tests.

**P2 — operational hygiene.**
10. Remove default credentials from `public/locales/*/translation.json` and rotate the accounts they name.
11. Return real HTTP status codes from `admin-create-user` and preserve `status` through the service-layer error mapping so the UI can branch on 401/403/404/409.
12. Add a `.env.example` listing `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` (and the documented-but-unused FastAPI variables), and move `verify_jwt`/function secrets into versioned `supabase/config.toml`.
13. Move `update-constraint.js` into `supabase/migrations/` as a timestamped migration so schema changes are replayable, and publish a real `data_dump.sql` (or a schema-only dump) so the base schema is reviewable.

**P3 — cleanup.**
14. Delete `supabase/migrations_backup/` (or move it outside `supabase/`), the executed `update-logo*.cjs` codemods, the empty `git` and `data_dump.sql`, and either restore or delete the broken Netlify/Vercel/Mongo paths (`netlify/functions/api.js`, `vercel.json` `/api` rewrite, `config/mongodb.js`).
15. Rewrite `README.md`, `Backend_Technical_Specification.md`, `SECURITY_IMPLEMENTATION.md`, `RATE_LIMITING.md` and `VALIDATION.md` against the authoritative `openapi_dump.json` and the actual Supabase actions, or move them to an `archive/` folder so nobody implements against a fictional Express server.
