# Deep review 1.1.1 — Flutter core, entry point and project configuration

## Scope

This leaf owns the application bootstrap (`lib/main.dart`, `lib/app.dart`), the whole shared foundation layer under `lib/core/` (constants, models, navigation, network, theme and reusable widgets), and the seven root-level project files that govern analysis, dependency resolution, tooling and VCS behaviour: `pubspec.yaml`, `pubspec.lock`, `analysis_options.yaml`, `.metadata`, `.flutter-plugins-dependencies`, `agriflow_admin.iml` and `.gitignore`. That is 26 files in total, enumerated by hand from `lib/core/**` rather than assumed, so nothing in the leaf's declared scope is skipped.

All backend claims in this document are checked against `openapi_dump.json` (94 paths), which is the only backend truth available to this review. Where a UI affordance in the core layer implies a backend capability that the OpenAPI does not define, this document states `Backend API required - to be supplied by Syed.` rather than inventing an endpoint, payload or table.

The gate contract read first was `.unlazy/deep-review/gates/leaf-1.1.1.md`, which fixes the scope (G2) and requires structure plus depth (G1) plus file:line evidence for every core widget, token and navigation entry (G3).

## Findings

### How the app boots, and how Admin vs Manager is decided

`lib/main.dart:9` is a bare `void main() async` that does three things before `runApp`: `WidgetsFlutterBinding.ensureInitialized()` (`lib/main.dart:10`), an awaited `SharedPreferences.getInstance()` (`lib/main.dart:11`), and then a hand-rolled dependency graph — `SharedPreferencesAuthLocalDataSource`, `FastApiAuthRemoteDataSource`, `AuthRepositoryImpl`, `AuthController` (`lib/main.dart:12`-`lib/main.dart:18`) — passed into `AgriFlowApp` (`lib/main.dart:20`). There is no `Provider`, no `Riverpod`, no `GetIt`; the single controller is injected positionally and re-shared downwards via constructor parameters. That is a defensible, dependency-free choice for an app of this size, but it means every screen must thread `AuthController` (or a feature controller) through its constructor, which is exactly what `lib/app.dart:47`-`lib/app.dart:66` and the two shells do.

The root widget is `MaterialApp` at `lib/app.dart:36` with `title: 'Sri Siva Sai Seeds — Admin & Manager'` (`lib/app.dart:37`), `debugShowCheckedModeBanner: false` (`lib/app.dart:38`) and exactly one theme: `theme: AppTheme.lightTheme` (`lib/app.dart:39`). There is no `darkTheme` and no `themeMode` anywhere in `lib/` — a grep for `darkTheme|themeMode|Brightness.dark` returns only three unrelated status-bar brightness calls in the auth screens. The app therefore hard-declares itself light-only.

Routing is not a router at all: `home:` selects `FoundationShowcaseScreen` when `showcaseMode` is true, else `AuthRouter` (`lib/app.dart:40`-`lib/app.dart:42`). `AuthRouter` is a `ListenableBuilder` over the controller (`lib/app.dart:70`-`lib/app.dart:72`) with a four-way state machine: initializing/session-restoring → `SplashScreen` (`lib/app.dart:75`-`lib/app.dart:77`), unsupported role → `UnsupportedRoleScreen` (`lib/app.dart:79`-`lib/app.dart:84`), authenticated → role branch, otherwise `LoginScreen` (`lib/app.dart:106`). The role decision itself is `lib/app.dart:86`-`lib/app.dart:103`: `role.isAdmin` returns `AdminShell`, `role == UserRole.manager` returns `ManagerShell`, anything else falls to `UnsupportedRoleScreen`. Note the asymmetry — the admin branch accepts `superAdmin` implicitly because `UserRole.isAdmin` is `admin || superAdmin` (`lib/core/models/user_role.dart:34`), while the manager branch is an equality test; the same union is re-expressed three different ways in `lib/app.dart:88`, `lib/app.dart:93` and `lib/app.dart:156`.

`AuthRouter` also constructs a `_UnconfiguredAuthRepository` when no controller was injected (`lib/app.dart:62`-`lib/app.dart:65`), whose `login` and `getCurrentUser` throw `UnimplementedError('Backend API required — to be supplied by Syed.')` (`lib/app.dart:119`, `lib/app.dart:140`). In practice `main.dart` always injects a real controller, so this fallback is only reachable by a caller that builds `AgriFlowApp()` without arguments — which today is only `test/widget_test.dart:14`, and it passes `showcaseMode: true`, so the fallback never executes.

Role parsing lives in `UserRole.fromString` (`lib/core/models/user_role.dart:12`-`lib/core/models/user_role.dart:25`): null → `unsupported`, hyphens normalised to underscores, `super_admin`/`superadmin` → `superAdmin`, `admin`/`administrator` → `admin`, `manager` → `manager`, everything else → `unsupported`. That mapping is load-bearing: `AuthController.currentRole` returns null for unsupported roles and the shell branch then routes to `UnsupportedRoleScreen`, so an unknown backend role can never silently become a Manager. That is the single most important safety property in the entry layer and it is correctly implemented.

### `lib/core/network/api_contracts.dart` is an orphaned parallel contract layer

The 265-line file declares 16 abstract repository interfaces — `IAuthRepository` (`lib/core/network/api_contracts.dart:11`), `IDashboardRepository` (`:36`), `ISeedPurchaseRepository` (`:44`), `IBookingSlotsRepository` (`:58`), `IFarmVisitsRepository` (`:79`), `IGrainSalesRepository` (`:104`), `ISeedsInventoryRepository` (`:122`), `IWarehouseRepository` (`:141`), `IBillingRepository` (`:161`), `IMarketRatesRepository` (`:178`), `IFarmersRepository` (`:186`), `IManagersRepository` (`:209`), `IReportsRepository` (`:230`), `IEventLogsRepository` (`:238`), `ICreditsRepository` (`:243`), `ICacheRepository` (`:256`).

A repository-wide search for the string `api_contracts` returns **zero imports**. Nothing in `lib/` or `test/` reads this file. Every one of those 16 interfaces has a differently-shaped twin under `lib/features/**/domain/repositories/` (18 repository files), and only the feature twins are wired up. The core file is documentation-shaped code that will silently drift.

Worse, its doc comments actively misstate the OpenAPI. Only `IAuthRepository`'s six members carry verified endpoint annotations (`lib/core/network/api_contracts.dart:12`, `:15`, `:18`, `:21`, `:24`, `:27`) and those six all match `openapi_dump.json` (`POST /api/v1/auth/login`, `POST /api/v1/auth/logout`, `GET /api/v1/users/me`, `POST /api/v1/auth/refresh`, `POST /api/v1/auth/forgot-password/send-otp`, `POST /api/v1/auth/forgot-password/reset`). Every other method is stamped `/// Backend API required — to be supplied by Syed.` even where the endpoint already ships: `getDashboardSummary` (`lib/core/network/api_contracts.dart:37`) is `GET /api/v1/admin/dashboard`, which returns `AdminDashboardResponse` with 15 concrete fields; `approveRequest`/`rejectRequest` (`:52`, `:55`) are `PATCH /api/v1/seed-purchases/{purchase_id}/status`; `getFarmVisits`/`scheduleVisit`/`updateVisitStatus` (`:81`, `:87`, `:96`) map to `/api/v1/farm-visits`, `/api/v1/farm-visits/{visit_id}/schedule` and `/complete`; `getGrainSales`/`logReceivedCrop`/`markSalePaid` (`:106`, `:109`, `:119`) map to `/api/v1/grain-sales`, `/procure` and `/{sale_id}/pay`; `getFarmers`/`registerFarmer`/`approveFarmerKYC` (`:188`, `:194`, `:203`) map to `/api/v1/farmers`, `POST /api/v1/farmers` and `/api/v1/farmers/{farmer_id}/approval`; `getManagers`/`createManager`/`updateManagerStatus`/`resetManagerPassword` (`:211`, `:214`, `:224`, `:227`) all exist; `getMonthlyReport` (`:232`) is `GET /api/v1/admin/reports/monthly`; `getAuditLogs` (`:240`) is `GET /api/v1/admin/audit-logs`; `getMarketRates`/`updateMarketRate` (`:180`, `:183`) are `GET`/`POST /api/v1/market-rates`. The blanket annotation is therefore wrong in both directions: it under-claims roughly a dozen live endpoints and, by the same token, gives no signal about the handful that genuinely do not exist.

Those genuinely missing capabilities are: `getRecentActivities` (`:41`), `adjustStock` as a delta operation (`:127` — `PATCH /api/v1/seeds/{seed_id}` is a `SeedUpdate` full-object patch, not a stock delta), `getWarehouseInventory` as a GET (`:146` — the spec exposes `POST /api/v1/warehouses/{warehouse_id}/inventory` only), `deleteFarmer` (`:206` — `/api/v1/farmers/{farmer_id}` exposes `get` only), `getInvoices` and `logTransaction` (`:163`, `:166` — there is no billing resource and `POST /api/v1/transactions` does not exist), `downloadReportPdf` (`:235`), and all of `ICreditsRepository` (`:243`-`:254`) and `ICacheRepository` (`:256`-`:265`). Backend API required - to be supplied by Syed.

### Tab, drawer and role policy are encoded three separate times

The same navigation fact is written down in three places that can disagree. First, `NavDestination` carries `adminTabIndex`/`managerTabIndex` (`lib/core/navigation/nav_destination.dart:16`-`:17`) with concrete values at `:43`, `:52`, `:61`, `:70`, `:163`. Second, `CustomTabbar.tabs` (`lib/core/widgets/custom_tabbar.dart:30`-`:83`) re-declares the ids, labels and icons as an independent list. Third, each shell hard-codes an index→route switch: `lib/features/admin/presentation/admin_shell.dart:148`-`:157` and `lib/features/manager/presentation/manager_shell.dart:148`-`:161`. Change a title in `nav_destination.dart:40` and the tab bar keeps the old label; add a tab and the switch silently misroutes.

The same duplication exists for permissions. `NavDestination.adminOnly` is set on five destinations (`lib/core/navigation/nav_destination.dart:107`, `:115`, `:131`, `:139`, `:147`) and consumed in exactly one place — `manager_shell.dart:170`. The drawer ignores the flag entirely and instead hand-writes its own role conditions at `lib/core/widgets/custom_drawer.dart:157`, `:167`, `:177` and `:185`. There is no shared predicate, so adding `adminOnly: true` to a destination will not hide it from the manager drawer.

## Theme and design tokens

`AppColors` (`lib/core/constants/app_colors.dart:25`-`:98`) is a faithful transcription of the approved HTML CSS variables, documented in the header comment at `lib/core/constants/app_colors.dart:4`-`:24`: `background #F3F6EC`, `surface #FFFFFF`, `surfaceAlt #E9F0DD`, the forest/canopy green ladder (`forest #15302A`, `forestSoft #1F4438`, `canopy #2E7D5B`, `canopyDeep #1F5C42`, `canopyLight #7BC79A`), warm accents (`amber #E39A3B`, `amberSoft`, `clay`, `claySoft`), text ramp (`text #1C2A21`, `textMuted #657268`, `textFaint #8B9689`), `line #E1E8D8`, `alert #D9704C`, status pairs `good/goodBg`, `warn/warnBg`, `bad/badBg`, the admin navy trio (`adminNavy #1E3A5C`, `adminNavyDeep #16293F`, `adminNavyLight #4C7BAA`) and `infoBg #E1EBF6`. It also owns layout tokens: radii `radiusSm/Md/Lg = 12/18/26` (`lib/core/constants/app_colors.dart:70`-`:72`) and three shadow lists `shadowSm`, `shadowMd`, `cardShadow` (`:75`-`:97`). Two naming aliases exist purely for HTML vocabulary parity — `goodLight = goodBg`, `warnLight = warnBg`, `badLight = badBg`, `primaryLight = canopyLight` (`:54`, `:57`, `:60`, `:61`) — and of those only `badLight` and `primaryLight` are ever read.

`AppTypography` (`lib/core/constants/app_typography.dart:9`-`:135`) delivers three families through `google_fonts`: Fraunces for `displayLarge/Medium/Small` (26/21/18px, `:11`, `:20`, `:29`), Manrope for `titleLarge/Medium/Small`, `bodyMedium`, `bodySmall`, `caption`, `eyebrow` and `button` (`:39`-`:108`), and JetBrains Mono for `monoLarge/Medium/Small` (`:111`-`:134`) used for money, IDs and deltas. Every one of the 14 methods has at least one real caller (counts range from 1 for `monoSmall` to 73 for `bodySmall`). Two quirks: `titleSmall` and `bodyMedium` are both 13.5px (`:59`, `:68`) and differ only in weight, and `eyebrow` computes `letterSpacing: 0.09 * 11` inline (`:97`) — a magic ratio with no named constant.

`AppTheme.lightTheme` (`lib/core/theme/app_theme.dart:6`-`:102`) builds a Material 3 light theme: `ColorScheme.light` seeded from `adminNavy`/`canopy` (`:12`-`:21`), `scaffoldBackgroundColor: AppColors.background` (`:11`), app bar (`:22`-`:29`), card (`:30`-`:38`), divider (`:39`-`:43`), elevated and outlined button themes (`:44`-`:66`), a fully specified `inputDecorationTheme` with separate enabled/focused/error borders at radius 14 (`:67`-`:93`) and a 30-radius bottom sheet (`:94`-`:100`). Critically it never sets a `textTheme` or `fontFamily`, so any widget that is not explicitly styled with `AppTypography` falls back to Roboto — concretely the SnackBar raised by `manager_shell.dart:171`-`:175`, tooltips (`lib/core/widgets/squircle_icon_button.dart:87`-`:90`) and any dialog. It defines no `snackBarTheme`, `dialogTheme` or `tabBarTheme`, and there is no dark counterpart at all (`lib/app.dart:39`).

The theme is also bypassed deliberately in six core files that call `GoogleFonts.*` directly instead of going through `AppTypography`: `lib/core/widgets/app_navbar.dart:84`, `:104`, `:116`; `lib/core/widgets/app_toast.dart:125`; `lib/core/widgets/custom_drawer.dart:75`, `:94`, `:106`, `:117`, `:215`, `:242`, `:294`, `:310`; `lib/core/widgets/custom_tabbar.dart:134`; `lib/core/widgets/status_pill.dart:122`. Finally, colour is not consistently tokenised: a grep for `0xFF` across `lib/` finds 114 hardcoded hex literals. The showcase alone invents off-palette colours such as `Color(0xFF0369A1)` and `Color(0xFFECF5FD)` (`lib/app.dart:502`-`:503`), `AppNavbar` rolls its own `Color.fromRGBO(21, 48, 42, …)` shadows instead of reusing `AppColors.shadowSm` (`lib/core/widgets/app_navbar.dart:42`, `:72`), `AppScaffold` paints its desktop letterbox `Color(0xFFDCE6C9)` (`lib/core/widgets/app_scaffold.dart:107`), and `state_views.dart:121` uses `Color(0xFFF5F8EF)` for the shimmer mid-stop.

## Navigation architecture

The destination model is `NavDestination` (`lib/core/navigation/nav_destination.dart:10`-`:27`), a value object with `id`, `title`, `icon`, a `NavSection` (`overview`, `operations`, `administration`, `account` — `:3`-`:8`), an `adminOnly` flag and the two nullable tab indexes. Nineteen destinations are declared as static consts: `home` (`:30`), `seedPurchase` (`:38`), `bookingSlot` (`:47`), `farmVisits` (`:56`), `grainSales` (`:65`), `seedsInventory` (`:74`), `warehouse` (`:81`), `billing` (`:88`), `marketRates` (`:95`), `reports` (`:102`, admin only), `eventLogs` (`:110`, admin only), `allFarmers` (`:118`), `managers` (`:126`, admin only), `credits` (`:134`, admin only), `cacheManagement` (`:142`, admin only), `notifications` (`:151`), `account` (`:158`), `settings` (`:166`), `help` (`:173`). They are collected into `allDestinations` (`:180`-`:200`) and looked up with `fromId` (`:202`-`:207`), which **silently falls back to `home` for an unknown id** — a typo or an out-of-scope route is indistinguishable from a deliberate dashboard navigation. `manager_shell.dart:169` then pairs that fallback with `_currentRoute = route` at `:181`, so an unknown route would render `ModulePlaceholderScreen` titled "Dashboard" while the shell believes it is elsewhere.

The chrome around those destinations is a three-part composition owned by `AppScaffold` (`lib/core/widgets/app_scaffold.dart:8`): `AppNavbar` as the app bar (`:64`), `CustomDrawer` as the side menu (`:76`), `CustomTabbar` as the bottom bar (`:92`). `AppScaffold` also contains the responsive strategy: below 480px wide it renders the raw scaffold (`:57`, `:100`-`:102`); above that it letterboxes the whole thing in a fixed 412×860 phone frame with a 52-radius bezel (`:106`-`:131`) — a desktop/tablet presentation that will clip content at large text scales.

`AppNavbar` (`lib/core/widgets/app_navbar.dart:7`) implements `PreferredSizeWidget` at a fixed 74px (`:24`) but adds `MediaQuery.paddingOf(context).top + 8` inside its own padding (`:30`), so the real height is status-bar + ~62. It draws a menu button (`:51`), a logo circle containing the literal letter `S` (`:82`-`:90`) rather than the `assets/images/sri_siva_sai_seeds_logo.png` asset that `pubspec.yaml:66` declares and the auth screens already use, the brand string `'Sri Siva Sai Seeds'` hardcoded at `:103`, the console title from `role.consoleTitle` (`:115`) and a notification bell with badge (`:127`-`:136`).

`CustomDrawer` (`lib/core/widgets/custom_drawer.dart:7`) is 82% of viewport width (`:34`) with a navy gradient header (`:46`-`:52`), an initials avatar derived from `userName[0]` (`:71`-`:81`), a role pill (`:92`-`:99`), grouped sections and a footer logout button (`:205`-`:230`). Its menu is hand-authored rather than derived: Operations lists nine items (`:144`-`:155`), then role-conditional `reports`/`eventLogs` for admin versus `allFarmers` for manager (`:157`-`:162`), then an Administration block for admin only (`:167`-`:174`), then Account (`:176`-`:186`) where `notifications` and `help` are hidden from admins (`:177`, `:185`) — yet `AppScaffold` unconditionally wires the navbar bell to `onNavigate('notifications')` (`lib/core/widgets/app_scaffold.dart:67`-`:69`), so an admin can reach a destination their own drawer does not list. Both shells pass `unreadNotifications: 0` and `pendingOrders: 0` (`admin_shell.dart:225`-`:226`, `manager_shell.dart:241`-`:242`), so the two badges the drawer renders (`:147`, `:181`) are permanently dead in production. Unread notification count for admin/manager roles: Backend API required - to be supplied by Syed. A pending seed-purchase order count: Backend API required - to be supplied by Syed.

`CustomTabbar` (`lib/core/widgets/custom_tabbar.dart:18`) renders four tabs for admins and five for managers (`:30`-`:83`), the fifth being `account` (`:76`-`:80`), matching the `managerTabIndex: 4` declared at `lib/core/navigation/nav_destination.dart:163`. Each tab is an icon, an 10.5px label (`:135`) and a 4px animated dot (`:143`-`:151`). Its `InkWell` sits directly on a decorated `Container` (`:96`, `:116`) with no local `Material`, unlike `AppCard.onTap` which correctly wraps in `Material` (`lib/core/widgets/app_card.dart:42`-`:50`); the same pattern appears in `SquircleIconButton` (`lib/core/widgets/squircle_icon_button.dart:43`-`:62`).
